# Proposal：移动端产品设计（FullSpec）

> 状态：草案（proposal）

面向Middle与KA销售的移动端商机查看、信息维护与行动管理

移动端围绕销售拜访和客户沟通场景展开，重点解决三件事：快速查看商机、及时补充商机信息、避免后续行动被遗漏。PC端CRM继续作为商机主数据来源，移动端不复制完整CRM，而是提供适合移动场景的轻量入口。

商机模块负责呈现当前商机上下文并承载商机小记维护；待办模块负责承载销售主动创建的事项以及系统按明确规则发现的遗漏事项；录入模块负责将录音、文本和文档整理为可写入商机的信息。

## 1. 产品背景

当前销售的商机信息主要依赖人工录入。销售通常在客户沟通结束后，再回到PC端CRM补写商机小记、更新字段或整理周报。由于Middle和KA销售经常在外拜访客户，信息录入容易被推迟到当天结束甚至周末，客户需求、沟通结论、承诺事项和下一步行动也容易因此遗漏。

销售最常进入商机系统的时机是更新商机和填写商机小记。移动端因此不应只是将PC端CRM缩小后搬到手机上，而应围绕客户沟通前后最常发生的动作，降低查看信息、记录信息和安排后续行动的成本。

项目长期目标还包括客户拜访信息沉淀、动态需求清单、商机事件流、销售与FDE协作以及基于高质量商机数据发现新商机。但这些能力都依赖稳定、及时、可信的输入。因此，现阶段首先验证移动端商机查看、小记维护和规则待办能否形成可使用的基础闭环。

## 2. 产品定位

移动端CRM的定位是：帮助销售在移动场景下快速了解商机、补充商机信息，并将需要继续处理的事项形成明确待办。

PC端CRM继续承载完整商机事实、后台配置和复杂管理能力。移动端只读取销售高频需要的信息，并提供有限、明确的写回能力。商机模块回答“这个商机现在是什么情况”，待办模块回答“接下来需要处理什么”，录入模块回答“客户沟通产生的信息如何低成本进入系统”。

## 3. 目标用户

### 3.1 核心用户

核心用户为Middle和KA销售。两类销售通常同时维护多个客户和商机，商机周期较长，沟通材料较多，也更需要持续跟进、信息沉淀和FDE协作。

### 3.2 后续协作用户

FDE是后续重要协作角色。销售在客户沟通中遇到技术方案、测试接入、部署或产品能力问题时，需要将完整商机背景传递给FDE。长期方案中，应允许FDE在同一商机上下文内查看必要信息并处理协作事项；现阶段不建设完整协作工作流。

## 4. 真实工作场景与核心问题

| **场景**           | **现有做法**                                           | **主要问题**                                                          |
|--------------------|--------------------------------------------------------|-----------------------------------------------------------------------|
| 客户沟通后记录信息 | 销售回忆沟通内容，手工写小记、补字段，再整理周报或文档 | 整理耗时，容易延迟录入；客户需求、Token消耗量、承诺事项等信息容易遗漏 |
| 外出时查看商机     | 回到电脑后查询PC端CRM，或依靠聊天记录和个人记忆        | 无法在拜访现场快速获取上下文，影响沟通连续性                          |
| 安排后续行动       | 使用个人备忘录、聊天消息或独立回访系统记录             | 商机与任务割裂，下一步容易遗漏，也难以回到具体商机                    |
| 处理长期未推进商机 | 销售凭经验定期回看，或等待系统统一提醒                 | 不同商机周期差异大；统一频繁提醒会产生噪声，完全依赖人工又容易遗忘    |
| 使用AI辅助销售     | 使用转写、摘要或外部工具，再手工搬运结果               | AI可能误解客户原意或过度推测，关键业务判断不能直接自动生效            |

## 5. 产品总体目标

### 5.1 长期目标

**客户拜访或沟通** → 多种材料进入录入模块 → **销售确认写入内容** →
更新商机信息 → **形成下一步行动** → 处理结果回到商机

长期目标能力包括：

客户拜访作为独立的信息容器，承载录音、文档、参与人、沟通内容、承诺和下一步。

一次拜访或一份材料可以关联一个或多个商机，不能默认一段录音只属于一个商机。

商机形成清晰的事件流和关键时间节点，帮助销售快速了解发生过什么。

需求清单随商机阶段变化，保留当前需求、历史需求和变化记录。

系统根据商机阶段和业务变化形成行动提示，并支持销售决定后续跟进周期、休眠或停止提醒。

销售与FDE围绕同一商机协作，减少背景信息重复转述。

在商机信息质量稳定后，基于已有商机特征辅助发现新客户和新商机。

### 5.2 现阶段MVP目标

现阶段先验证两个问题：销售是否愿意在移动端查看和补充商机信息；简单、明确的待办是否能够减少商机和录入事项的遗漏。

**查看商机** → 查看或补充商机小记 → **创建下一步行动** →
进入我的待办处理

**系统按明确规则发现遗漏** → 自动生成我的待办 →
**销售处理或业务动作自动完成**

## 6. 总体设计原则

1. 围绕真实操作节点设计。功能优先嵌入查看商机、写小记和处理待办等已有路径，不单独建设低频“AI中心”。

2. 每个页面聚焦一个主要任务。商机列表用于找商机，商机详情用于理解和补充商机，待办列表用于处理行动。

3. AI先帮助记录和整理，不替销售做关键业务判断。阶段、客户需求和关键事实未经确认不得自动改变。

4. 商机是具体项目或业务机会，不是客户全部信息的集合；同一客户可以有多个商机。

5. 待办是行动承载，不是复杂项目管理、审批或绩效监督系统。

6. 现阶段规则必须简单、明确、可验证；长期能力保留，但需要写清现阶段不做的原因和进入条件。

## 7. 录入模块

### 7.1 动机 / 用户故事

销售在线下拜访中会产生录音、图片、文件和口头结论，但回到系统后仍要手工整理并填写商机小记/字段，成本高、易遗漏、难追溯。

一句话需求：

> 销售能以尽量低的操作成本，把拜访材料沉淀为可核查的商机信息，并可靠写入 CRM。

典型故事：
1. 拜访中先录音，结束后补图片与口述，再关联商机并生成小记写入。
2. 拜访后打开未完成草稿，继续补材料、核查信息并提交。
3. 从草稿箱找回某次拜访草稿，继续录入或删除。


### 7.2 目标用户

一线销售（手机端使用，主场景为拜访中与拜访后）。


### 7.3 现有做法及其不足

| 现有做法 | 不足 |
|----------|------|
| 拜访中用手机录音 / 备忘录，事后再打开 PC 商机系统补录 | 材料与商机割裂，补录成本高 |
| 在 PC 端手工写商机小记、改字段 | 无法在现场完成闭环，信息容易遗忘 |
| 材料散落在微信、相册、本地文件 | 难分类、难回溯、难与某次商机绑定 |


### 7.4 本期范围与明确不做

#### 7.4.1 本期做（录入模块）

1. **草稿管理**：新建、查看、继续编辑、删除、自动保存；草稿箱作为录入模块能力。
2. **材料录入**：录音、图片、文件、口述的增加与删除。
3. **商机关联**：选择 / 搜索已有商机并绑定到草稿。
4. **信息处理**：基于材料为**一个**已关联商机生成待核查的商机字段与商机小记（可用异步任务；首期允许部分能力 mock）。
5. **信息核查**：修改、置空、补充字段与小记。
6. **预览与写入 CRM**：确认后写入；写入成功后保留必要录入结果，草稿按规则关闭或销毁。

#### 7.4.2 本期不做

| 不做项 | 说明 |
|--------|------|
| 「我的」业务模块 | 导航可保留「我的」入口；草稿箱不归「我的」 |
| 日报 / 周报 | 不做生成与编辑；若导航预留入口，显示为空或「即将支持」 |
| 从草稿提取待办清单并自动转为待办 | 待办的生成与规则由待办模块负责，录入不解析、不创建待办 |
| 一个草稿对多商机提取信息 | 默认一次拜访只涉及一个商机；一个草稿只关联并服务一个商机 |
| 商机经营能力 | 商机列表/详情/收藏等由商机模块负责；录入仅调用「选择/搜索商机」 |
| 待办规则本身 | 「未完成草稿待办」「七天未跟进」由待办模块负责；录入可被待办拉起继续编辑 |
| 新建商机（若商机模块未提供） | 本期默认关联已有商机；是否支持移动端新建商机，等商机模块定稿 |
| 需求清单录入 | 商机详情中需求清单一期不做，录入也不产出该类对象 |
| 多账号体系、复杂权限配置 | 不做 |
| iOS / 鸿蒙首期必达 | 产品行为按移动端定义；平台交付节奏另见技术选型 |


### 7.5 关键决策与依据

#### 7.5.1 决策 A：以「录入草稿」为唯一主对象贯穿全流程

| 备选 | 内容 |
|------|------|
| A1 | 采集草稿 / 信息草稿两套对象 |
| A2 | 单一「录入草稿」，用阶段表达进度 |

**选择：A2**

理由：
- 销售感知是「一次拜访录入」，不是两套草稿体系。
- 录音自动建稿与手工建稿都是同一对象的不同创建方式。
- 降低草稿箱理解成本。

#### 7.5.2 决策 B：草稿进度用「流程阶段 + 条件」表达，不用内容组合当状态名

| 备选 | 内容 |
|------|------|
| B1 | 空草稿 / 有素材 / 有素材且已关联… 等组合状态 |
| B2 | 流程阶段（如编辑中、已关联、处理中、核查中、待预览、写入中、已完成）+ 是否有素材、是否已关联等条件 |

**选择：B2**

理由：
- 组合状态会随能力增加爆炸，回退规则难维护。
- 阶段表达销售当前走到哪一步；条件用于按钮可用性判断。

**本期阶段（最小集）：**

```text
editing        编辑材料中（可未关联商机）
bound          已关联商机，待处理或处理完成进入核查
processing     信息处理中
reviewing      信息核查中
previewing     预览确认中
committing     写入中
committed      已写入完成
```

规则：
- 采集材料阶段允许尚未关联商机。
- 未关联商机前，不可进入信息处理与写入。
- 无有效材料时，不可进入信息处理。
- 核查未确认，不可进入预览。
- 预览未确认，不可写入。
- 一个草稿最多关联一个商机；关联后若更换商机，需明确覆盖原关联（不做一稿多商机）。
- 写入成功后草稿进入 `committed`（或从草稿箱移除）。

#### 7.5.3 决策 C：字段与小记不各建一套独立业务状态机

| 备选 | 内容 |
|------|------|
| C1 | 商机字段、商机小记各自维护完整状态机 |
| C2 | 二者作为草稿在某次「提取结果」上的内容，编辑受草稿阶段约束 |

**选择：C2**

理由：
- 用户确认的是「这一稿能不能写」；字段/小记拆两套状态徒增复杂度。
- 回退以草稿阶段回退为准。

#### 7.5.4 决策 D：信息采集时可以先不关联商机

| 备选 | 内容 |
|------|------|
| D1 | 必须先选商机，才能开始录音或添加材料 |
| D2 | 可先录音 / 添加材料并保存在草稿中，稍后再关联商机 |

**选择：D2**

理由：
- 拜访现场往往来不及先找商机，应允许先完成采集。
- 草稿先承载材料，关联商机后再做信息处理与写入，仍能保证写入目标唯一。
- 与「一稿一商机」不冲突：关联发生在处理前，且仅允许一个商机。

#### 7.5.5 决策 E：与外部模块的边界

| 对象 | 录入模块 | 外部模块 |
|------|----------|----------|
| 录入草稿、材料、提取结果、写入动作 | 可选可改可写 | 待办可拉起「继续编辑」；商机提供搜索/选择 |
| 商机主数据、收藏 | 只读引用 / 选择 | 商机模块 |
| 待办生成与提醒规则 | 不拥有 | 待办模块 |
| 日报 / 周报 | 不拥有 | 本期不做 |

录入模块对外：
- **输入**：用户操作；外部传入的草稿 ID（如待办跳转继续编辑）。
- **输出**：写入 CRM 后的商机小记（及本期允许写回的字段）；草稿状态变化可供待办感知（具体契约待待办模块对齐）。
- **不做**：从草稿内容抽取待办清单并自动建待办。


### 7.6 基本概念与信息结构

#### 7.6.1 概念定义

| 概念 | 定义 |
|------|------|
| 录入草稿（IntakeDraft） | 一次录入任务的聚合根，承载材料、关联商机、提取结果与流程阶段；一稿至多一个商机 |
| 录入材料（Material） | 录音 / 图片 / 文件 / 口述等原始材料 |
| 提取结果（Extraction） | 由材料生成的、面向该草稿已关联商机的字段集合 + 商机小记，供核查 |
| 商机字段（草稿内） | 待写入或对比展示的结构化字段，尚未等于 CRM 最终值 |
| 商机小记（草稿内） | 待写入 CRM 的小记文案 |
| 草稿箱 | 当前用户未完成（未 committed）草稿列表，属于录入模块 |

#### 7.6.2 信息结构（逻辑）

```text
IntakeDraft
- id
- name
- stage
- opportunity_id?          // 至多一个
- materials[]
- extraction?
  - fields[]
  - note
- created_at / updated_at
- create_source: manual | from_recording | from_todo ...

Material
- id
- draft_id
- kind: audio | image | file | oral
- upload_status
- parse_status
- size / created_at
- oral_text? / file_ref?
```

#### 7.6.3 主流程（文字）

```text
进入录入
→ 新建草稿 或 从草稿箱继续
→ 增删材料（录音/图片/文件/口述）        // 此时可不关联商机
→ 关联唯一商机（列表选择或搜索）
→ 信息处理，得到字段与小记
→ 核查修改
→ 预览确认
→ 写入 CRM
→ 草稿关闭；结果在商机侧可见
```

快速录音路径：开始录音 → 结束录音 → 自动进入/创建带该录音的草稿（可不先选商机）→ 后续同上。

#### 7.6.4 一个真实例子

**现状：**  
销售拜访后手机里有 1 段录音、2 张白板照片，晚上回公司打开 PC，边听录音边写小记，常漏掉预算与竞品信息。

**提议后：**  
1. 拜访结束在手机结束录音，系统生成草稿 D1（含该录音，此时尚未关联商机）。  
2. 补充 2 张图片与一句口述「客户倾向私有化，8 月底前要报价」。  
3. 搜索并关联唯一商机「星海科技-AI Coding」。  
4. 信息处理后得到字段（预算、部署方式等）与小记草稿。  
5. 销售改掉预算数字，确认预览后写入。  
6. 草稿 D1 关闭；商机时间线出现新小记，字段按写入规则更新。

**边界 / 非法：**
- 未关联商机时点击「开始处理」或「写入」→ 不可进行，提示先关联。  
- 无任何材料时点击「开始处理」→ 不可处理。  
- 试图为同一草稿关联第二个商机并行提取 → 不支持；仅允许更换唯一关联。  
- 写入中重复点击提交 → 只产生一次有效写入。  
- 已 committed 草稿 → 不可再作为可编辑草稿打开（查看历史走商机侧）。  
- 期望系统从草稿自动抽出待办事项 → 本期不提供。

## 8. 商机模块

### 8.1 动机与用户故事

销售在拜访客户前需要快速了解商机当前情况，在沟通结束后需要及时补充商机小记，并明确下一步行动。目前这些操作主要依赖PC端CRM，移动场景下操作不便。移动端商机模块需要将销售最常使用的信息和动作集中起来，但不复制PC端全部功能。

### 8.2 商机定义

商机是客户侧一个相对独立、具有明确业务目标的项目、产品应用或系统运维机会。一个客户可以有多个商机，所有小记、待办和业务操作必须落到具体商机，不能只关联客户UID。

商机也不应拆分得过细。多个属于同一项目、共同影响同一成交结果的需求，应保留在一个商机内。一次录音或客户拜访可能同时涉及多个商机，长期需要支持多商机关联；现阶段不自动识别和拆分商机归属。

### 8.3 现阶段信息架构

| **页面或区域** | **主要内容**                           | **主要目的**                   |
|----------------|----------------------------------------|--------------------------------|
| 商机列表       | 搜索、基础筛选、收藏状态、商机卡片     | 快速找到需要查看的商机         |
| 商机详情       | 基本信息、商机小记、需求清单、关键字段 | 快速理解当前商机并补充信息     |
| 创建下一步行动 | 待办标题、待办时间、补充说明、当前商机 | 把商机中的后续事项直接转成待办 |

### 8.4 商机列表

商机列表用于帮助销售快速找到需要查看的商机。列表不展示大量长文本，也不增加“今日跟进”等与待办重复的入口。

提供商机搜索和基础筛选。

列表卡片展示商机名称、客户或对接人、当前阶段、商机等级、预计金额和最近跟进时间。

保留收藏状态，方便销售回到重点商机。

同一客户下的多个商机分别展示，进入详情后只呈现当前商机上下文。

### 8.5 商机详情

#### 8.5.1 商机基本信息

基本信息用于帮助销售快速确认当前商机，建议包含：商机名称、客户、负责人、联系人、商机阶段、商机等级、商机类型、预计金额和最近跟进时间。

现阶段不展示预计成交日期。现有数据准确性不足，不能作为可靠判断依据，也不应据此生成筛选或待办。

#### 8.5.2 商机阶段

| **阶段** | **含义**                                         |
|----------|--------------------------------------------------|
| 初步接触 | 商机已建立，销售开始与客户建立联系并确认基本情况 |
| 技术提案 | 围绕客户场景提出技术或产品方案，持续沟通方案内容 |
| 测试接入 | 客户进入测试、验证、POC或实际接入阶段            |
| 报价确认 | 方案基本明确，进入价格、合同或商务条件确认       |
| 充值消费 | 合同签订后进入正式合作、首次充值或实际消费阶段   |

现阶段不使用AI自动识别或修改阶段。阶段变更必须由销售主动选择，或由现有CRM中的明确业务动作产生。移动端是否直接支持修改阶段，需要结合现有CRM权限和接口确认；产品原则是系统不得自行修改。

#### 8.5.3 商机小记

商机小记是销售当前最常维护的商机信息，也是后续需求整理、待办规则和周报总结的重要输入。

查看历史商机小记。

新增商机小记，并将内容写回PC端CRM。

编辑权限范围内的历史小记，并将修改结果写回PC端CRM。

区分“新增小记”和“编辑历史小记”；后续小记数量规则只统计新创建的小记。

长期可将小记用于自动总结周报，但周报生成不属于本期商机模块范围。

#### 8.5.4 需求清单

长期目标中，需求清单用于展示客户在不同商机阶段的结构化需求，并保留需求变化。需求属于客户项目要求，不是待办任务。

现阶段只保留需求清单的页面位置和空状态，不进行自动需求提取、需求编辑、当前与历史需求分类或需求证据展示。原因是需求定义、输入来源和准确性仍未稳定，过早生成需求容易把AI推测当成客户事实。

#### 8.5.5 关键字段

关键字段由PC端CRM或上游模块提供，移动端按“字段名称＋字段值”展示。

现阶段只读，不提供编辑入口。字段的补充和修改由录入模块或PC端CRM负责，避免商机详情承担过多录入职责。

#### 8.5.6 创建下一步行动

销售可在商机详情点击“创建下一步行动”。进入后默认带入当前商机，销售填写待办标题、待办时间和必要的补充说明。提交后，任务进入“我的待办—待处理”。

### 8.6 关键决策与取舍

| **设计点**     | **备选方案**                                                         | **现阶段选择与理由**                                                  |
|----------------|----------------------------------------------------------------------|-----------------------------------------------------------------------|
| 移动端商机范围 | 完整复制PC端CRM；只显示名称与阶段；**展示高频信息块**                | 选择高频信息块。完整复制会造成页面复杂，信息过少又无法支持销售判断    |
| 商机阶段       | AI自动修改；AI建议后确认；**使用CRM现有阶段**                        | 现阶段使用CRM现有阶段，不建设识别结果页。沟通记录不能代表完整业务事实 |
| 需求清单       | 现阶段自动提取；完全删除；**保留位置和空状态**                       | 保留位置和长期方向，但暂不生成内容。先保证输入稳定，再验证需求结构化  |
| 关键字段       | 详情页可编辑；**详情页只读**；不展示                                 | 选择只读。字段有查看价值，但编辑应由录入模块或PC端CRM承担             |
| 多商机关联     | 系统自动拆分；销售每次手工拆分；**现阶段单商机写入、长期支持多关联** | 现阶段避免复杂自动判断；数据关联以具体商机ID为基础，为后续多关联预留  |

### 8.7 长期演进

| **能力**             | **长期价值**                           | **现阶段不做的原因**                           | **现阶段预留**                             |
|----------------------|----------------------------------------|------------------------------------------------|--------------------------------------------|
| 商机事件流           | 快速查看商机发生过什么以及关键时间节点 | 事件来源和事件定义尚未完全打通                 | 保留小记时间、阶段更新时间和商机ID         |
| 动态需求清单         | 呈现当前需求、历史需求和变化           | 原始输入和需求口径不稳定，自动生成准确性不足   | 保留需求清单位置和商机关联                 |
| 客户拜访对象         | 完整承载一次沟通中的多种材料和信息     | 需要独立实体、事件流和多材料关系，影响范围较大 | 录入模块保留材料、时间和商机引用           |
| 一次材料关联多个商机 | 解决一段录音涉及多个项目的问题         | 自动归属准确性和交互成本尚未验证               | 所有写入以商机ID关联，后续可扩展多对多关系 |
| FDE协作              | 减少背景重复转述，提高技术响应效率     | 责任人、状态和协作流程涉及其他模块             | 商机上下文和待办保留可传递的商机ID         |
| 基于商机发现新客     | 从优质商机特征中发现相似机会           | 依赖长期稳定且完整的商机数据，当前输入质量不足 | 优先提升小记和字段完整度                   |

## 9. 待办模块

### 9.1 动机与用户故事

销售同时维护多个商机，容易遗漏商机长期未推进、录入草稿未完成、重点商机长期没有新增小记以及沟通后没有形成下一步行动等事项。现有商机系统与回访、任务系统割裂，销售需要依靠个人备忘录或记忆继续处理。

待办模块需要提供一个简单统一的行动入口，但不建设复杂项目管理、审批或绩效监督系统。

### 9.2 现阶段结构与来源

| **对象** | **内容**                                         |
|----------|--------------------------------------------------|
| 待处理   | 尚未完成的手动待办、商机下一步行动和系统规则待办 |
| 已完成   | 已经由销售完成或由业务动作自动完成的待办         |

现阶段待办来源包括：销售在待办模块手动创建；销售在商机详情创建下一步行动；系统根据明确业务规则自动生成。系统自动生成的任务直接进入“我的待办”，只增加“系统生成”标识，不设置单独的系统建议页面。

待办数据不只保存在当前移动设备。现阶段即通过服务端接口统一存储，移动端本地数据仅作为临时缓存和界面展示使用。用户更换设备或重新安装应用后，登录同一账号即可从服务端恢复待处理和已完成待办。

### 9.3 待办卡片

| **卡片类型** | **现阶段展示内容**                                                 | **现阶段不展示**                                         |
|--------------|--------------------------------------------------------------------|----------------------------------------------------------|
| 待处理       | 标题、关联商机或关联对象、待办时间、系统生成标识、一个主要处理动作 | 系统生成原因、当前商机状态、处理进度、完成方式、操作日志 |
| 已完成       | 标题、关联对象、完成时间                                           | 详细完成说明、自动或手动完成方式、历史操作日志           |

### 9.4 系统生成规则

#### 9.4.1 商机阶段长时间未变化

系统读取商机当前阶段和该阶段的最后更新时间。超过典型周期仍未发生阶段变化时，生成一次检查型待办。固定阈值的目的不是要求商机必须在规定时间内推进，而是提醒销售重新检查该商机是否需要继续跟进。

| **商机情况**             | **现阶段触发时间** | **说明**                                                         |
|--------------------------|--------------------|------------------------------------------------------------------|
| SDR分配的初步接触商机    | 当天               | 当天未完成有效触达时生成待办；有效触达的判断方式需与现有数据确认 |
| KA自主拓展的初步接触商机 | 不设统一阈值       | 自拓商机建立和触达时间差异较大，现阶段不强行统一                 |
| 技术提案                 | 14天               | 常见周期为1至2周；部分项目更长，14天先生成一次检查待办           |
| 测试接入                 | 14天               | 常见周期为1至2周；部分项目可持续1个月，14天先检查一次            |
| 报价确认                 | 7天                | 常见周期约1周                                                    |
| 充值消费                 | 14天               | 合同签订后通常1至2周进入正式合作；需结合首次充值或实际消费判断   |

同一商机、同一阶段只存在一条未完成的系统待办，不按天重复生成。

商机阶段发生变化后，原阶段停止计时，新阶段重新开始计时。

完成待办不会自动修改商机阶段。

该类待办由销售手动完成。

充值消费阶段需要额外判断是否已经完成首次充值或产生实际消费；已完成则不生成。

#### 9.4.2 录入草稿未完成

当录入模块中存在尚未提交的草稿时，生成一条待办。点击“去处理”后进入对应草稿；草稿成功提交后，待办自动进入已完成。草稿在何时生成待办，需要在开发前与录入模块统一口径。

#### 9.4.3 A+编程类商机小记不足

当商机同时满足以下条件时，生成待办：商机等级为A+；商机类型属于编程类，包括AI-coding；当前统计周期内新增小记少于两篇。

点击“去补充”后进入对应商机详情。当统计周期内新增小记达到两篇后，待办自动完成。编辑历史小记不计入新增数量。“一周”采用自然周还是滚动七天，需要在开发前统一口径。

### 9.5 待办完成规则

| **待办来源**           | **完成方式**                         |
|------------------------|--------------------------------------|
| 手动创建               | 销售手动完成                         |
| 商机详情创建下一步行动 | 销售手动完成                         |
| 商机阶段停留超时       | 销售手动完成                         |
| 录入草稿未完成         | 草稿提交成功后自动完成               |
| A+编程类商机小记不足   | 统计周期内新增小记达到两篇后自动完成 |

自动完成只改变待办状态，不自动修改商机阶段或其他业务字段。

### 9.6 关键决策与取舍

| **设计点**   | **备选方案**                                                               | **现阶段选择与理由**                                                                                                                                                         |
|--------------|----------------------------------------------------------------------------|------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| 系统事项去向 | 单独系统建议；销售确认后加入待办；命中规则后直接生成待办                   | 现阶段直接生成待办。当前规则数量少、条件明确，增加建议层只会增加操作步骤                                                                                                     |
| 提醒方式     | 应用内待办；App推送；本地通知和服务端提醒                                  | 现阶段只生成应用内待办。先验证规则是否有价值，避免大量通知形成噪声                                                                                                           |
| 跟进周期     | 所有商机统一周期；按阶段固定阈值；完全由销售设置；系统首次触发后由销售决定 | 现阶段按阶段固定阈值完成第一次检查；长期采用系统发现、销售决定后续策略                                                                                                       |
| 协作能力     | 完整协作任务；基础分配；个人待办                                           | 现阶段聚焦个人待办，避免演变成复杂项目管理系统                                                                                                                               |
| 完成记录     | 完成后删除；进入已完成；保留完整操作日志                                   | 现阶段进入已完成并展示完成时间，不建设复杂日志                                                                                                                               |
| 待办数据存储 | 仅保存在移动设备；等待Web端建设后再存储；先建设通用服务端存储              | 选择先建设通用服务端存储。Web端当前没有待办页面，但待办数据不能依赖单台设备。本地只作缓存，服务端作为统一记录来源，既支持换机同步，也为后续Web端复用同一数据和接口保留基础。 |

### 9.7 长期演进

| **能力**             | **长期价值**                               | **现阶段不做的原因**                         | **现阶段预留**                     |
|----------------------|--------------------------------------------|----------------------------------------------|------------------------------------|
| 自定义下一次检查时间 | 适应一个月、三个月、半年等不同商机周期     | 需要先验证第一次规则待办是否有效             | 阶段待办保留商机ID和阶段信息       |
| 休眠与重新激活       | 让低优先级或暂时无法成交的商机退出频繁跟进 | 涉及商机状态、CRM边界和重新激活规则          | 现阶段完成待办不改变商机状态       |
| 停止提醒             | 避免明确低价值商机持续产生任务             | 需要明确权限、恢复机制和规则范围             | 系统规则可按商机维度去重           |
| 阶段行动模板         | 在测试、报价等阶段提示标准动作             | 不同业务动作尚未标准化，直接生成容易产生噪声 | 现阶段先验证少量明确规则           |
| 跨商机待办           | 承载同时影响多个商机的事项                 | 多商机关联和责任边界尚未稳定                 | 待办结构保留关联对象类型           |
| 销售与FDE协作事项    | 减少背景重复转述并明确责任人               | 涉及协作流程、权限和状态                     | 待办保留商机上下文                 |
| 通知与提醒           | 在关键节点主动触达销售                     | 通知频率和价值尚未验证，容易形成打扰         | 待办保留时间字段，后续可接提醒能力 |

## 10. 模块关系与信息流

### 10.1 PC端CRM与商机模块

PC端CRM提供商机列表、商机基本信息、商机阶段、商机等级和类型、商机小记、关键字段以及用户权限。移动端读取上述数据，并将新增或修改的商机小记写回CRM。

### 10.2 商机模块与待办模块

商机详情可创建下一步行动，并将当前商机ID带入待办。系统规则也根据商机阶段、等级、类型和小记数据生成待办。

### 10.3 录入模块与待办模块

录入模块向待办模块提供草稿ID和草稿状态。草稿提交成功后，待办模块将对应任务自动完成。

### 10.4 录入模块与商机模块

录入模块负责处理录音、文本和文档，并由销售确认最终写入内容。长期可一次写入商机小记、关键字段、需求和下一步行动。商机模块不重复建设完整录入流程。

### 10.5 待办数据存储与多端同步

现有Web系统尚未提供待办模块，但移动端待办仍需要从现阶段开始统一存储到服务端。待办能力应独立于具体终端建设，移动端先通过通用接口使用，后续Web端可以在不迁移本地数据的情况下直接接入同一套待办数据。

服务端是待办数据的统一记录来源，保存待办归属用户、来源、关联对象、时间、状态和完成时间等必要信息。移动端本地存储只承担短期缓存，不作为最终事实来源，也不能因为更换设备、卸载应用或本地数据损坏而导致待办丢失。

用户登录后，移动端按当前账号从服务端获取待处理和已完成待办。创建、编辑、完成以及业务动作触发的自动完成都需要写回服务端。网络异常时，不得将仅保存在本地的结果静默视为同步成功，应明确显示未同步状态并允许重新提交。

| **场景**           | **数据行为**                                             | **产品要求**                                             |
|--------------------|----------------------------------------------------------|----------------------------------------------------------|
| 创建或编辑待办     | 移动端向服务端提交变更，服务端返回统一待办标识和最新状态 | 保存成功后再作为正式待办展示；重复提交不得生成重复任务   |
| 完成待办           | 手动完成或业务动作自动完成均写回服务端                   | 同一状态可在其他设备和未来Web端同步查看                  |
| 更换设备或重新安装 | 用户登录同一账号后从服务端重新获取待办                   | 原设备上的待处理和已完成记录不因换机丢失                 |
| 后续接入Web端      | Web端复用同一待办接口和服务端数据                        | 不再从移动端本地数据迁移，也不建立两套相互独立的待办记录 |

## 11. 现阶段明确不做

| **能力**                             | **现阶段不做的原因**                                       |
|--------------------------------------|------------------------------------------------------------|
| AI自动识别或修改商机阶段             | 沟通记录不能代表完整业务事实，销售对AI过度判断存在明确担忧 |
| 独立商机识别结果页面                 | 现阶段不做阶段识别，页面没有必要存在                       |
| 需求自动提取和需求管理               | 输入、需求定义和准确性尚未稳定，容易把推测当成事实         |
| 关键字段编辑                         | 字段编辑属于录入模块或PC端CRM，避免重复入口                |
| 预计成交日期及相关规则               | 现有数据准确性不足，不能作为可靠产品依据                   |
| 独立系统建议模块                     | 现阶段规则少且明确，增加建议层会增加操作成本               |
| App消息推送、稍后提醒和已设提醒页面  | 先验证应用内待办价值，避免通知噪声                         |
| 协作任务和复杂负责人机制             | 现阶段聚焦个人行动，协作涉及FDE流程和权限                  |
| 复杂优先级评分和智能排序             | 缺少稳定反馈数据，当前规则不需要模型排序                   |
| 商机休眠库、自定义长期周期和停止提醒 | 需要先验证第一次检查待办，并统一CRM状态边界                |
| 客户拜访独立实体和多商机关联         | 涉及独立数据结构、材料关系和复杂交互                       |
| 完整商机事件流                       | 事件来源和定义尚未完全打通                                 |
| 基于商机画像发现新客户               | 依赖稳定、完整的历史商机数据，当前应先改善输入质量         |

## 12. 总体验收

### 12.1 录入模块

1. 销售可新建草稿，并添加录音、图片、文件、口述中的至少一类材料；添加材料前不必先选商机。  
2. 结束录音后可进入草稿继续编辑，录音材料可见。  
3. 草稿箱展示未完成草稿；可继续编辑或删除。  
4. 可为草稿关联一个已有商机（含搜索不到时的空态）；不可对同一草稿同时服务多个商机的提取。  
5. 关联且有材料后，可发起信息处理并进入核查；字段与小记可改、可置空。  
6. 预览确认后可写入；写入成功后草稿不再出现在可编辑草稿箱。  
7. 写入成功后，对应商机侧可看到本次小记（字段写回范围以实现时与商机模块对齐的清单为准）。  
8. 未关联商机或无材料时，不能完成信息处理与写入。  
9. 不提供「从草稿生成待办清单并自动转待办」的能力。  
10. 导航上的日报/周报若存在，不提供可用功能（空态即可）。  
11. 「我的」不承载草稿箱；草稿箱只在录入模块中提供。

### 12.2 商机模块

1. 销售能够查看有权限的商机列表并进入详情。  
2. 商机详情能够展示基本信息、商机小记、需求清单空状态和关键字段。  
3. 销售能够新增商机小记，并将内容写回PC端CRM。  
4. 销售能够编辑权限范围内的历史小记，并将修改结果写回PC端CRM。  
5. 关键字段只展示，不出现编辑入口。  
6. 需求清单不生成虚构内容或未经确认的客户需求。  
7. 销售能够从商机详情创建下一步行动。  
8. 同一客户下的多个商机不会串联小记和待办。

### 12.3 待办模块

1. 销售能够查看待处理和已完成待办。  
2. 销售能够手动创建待办。  
3. 销售能够从商机详情创建下一步行动。  
4. 系统生成待办具有明确标识。  
5. 同一商机、同一规则不会重复生成未完成待办。  
6. 草稿提交后，对应待办自动完成。  
7. A+编程类商机新增小记达到要求后，对应待办自动完成。  
8. 阶段停留超时待办能够由销售手动完成。  
9. 已完成待办保留在已完成列表，不无痕消失。  
10. 现阶段不出现推送、提醒时间、协作人和复杂处理状态。  
11. 待办创建、编辑和完成后能够同步保存到服务端，不以单台移动设备的本地数据作为唯一记录。  
12. 用户在新设备登录同一账号后，能够继续查看和处理原有的待处理与已完成待办。

### 12.4 跨模块整体闭环

1. 产品能够完成“查看商机—维护小记—创建下一步行动—处理待办”的基础闭环。

2. 商机信息以PC端CRM为准，移动端不建立相互冲突的商机事实。

3. 一个客户下的多个商机在小记、待办和数据关联上保持隔离。

4. 现阶段系统待办只来自已确认的明确规则，不引入未经验证的AI判断。

5. 自动完成待办只改变任务状态，不静默修改商机阶段和业务字段。

6. 长期需求、事件流、客户拜访、协作和个性化跟进能力均保留演进方向，同时写清现阶段不做的原因。

7. 现阶段决定先设计上述三个模块，暂不设计“我的”模块。
